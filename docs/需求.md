## 交付内容

项目在 `wechat-lowlevelcv/`，四个产出点对应你的四项要求：

**1. 系统架构** — FastAPI + APScheduler + SQLite + OpenAI 兼容客户端（DeepSeek/通义/智谱都能换），单机 `uvicorn app.api:app` 即起，带运营控制台。选型理由写在 README 第 1 节，核心思路是「运营改配置不改代码」：题词表、阈值、数据源、排期、主题色全在 `config/topics.yaml`。

**2. 爬虫层** — `app/sources/` 每源一个模块：
- `lowlevelcv.py`：实测过页面结构（`h3` 标题 + `sumBox` 摘要 + `imgBox` 图 + `m1/m2` 链接），`?current=N` 翻页，测试用真实页面夹具

- `competitions.py`：Kaggle API / 天池 / 搜索 / NTIRE·MIPI 策展页

**3. Prompt 模板** — `app/llm/prompts.py`：一个共享 System（人设+文风+事实纪律）+ 三张模块任务卡，输出约束成 `ArticleSpec` JSON。**模型只写内容，排版交给模板**，这样每期版式不会飘。强 JSON mode + 括号配平修复 + 失败回传自修。

## 修订（2026-10-20）：配置 .env 后 demo 卡死——LLM 直连 + 流式成稿

用户配好 LLM 凭证后 `python -m scripts.demo` 长时间无输出，逐层排查出三个叠加根因，全部修复：

1. **公司上网代理劫持内网网关**：httpx 默认 `trust_env=True` 读系统代理，对内网 AI 网关的请求被上网代理拦截页（整页 HTML）顶掉。新增 `LLM_TRUST_ENV` 开关（`app/config.py`），`LLMClient` 改传 `http_client=httpx.AsyncClient(trust_env=…, verify=…)`（TLS 策略与抓取侧一致）；内网网关在 `.env` 设 0 直连（实测 0.3s 通）。SDK 异常统一经 `LLMClient._brief()` 压成一行，HTML 拦截页提取 `<title>` 并附直连提示，不再刷屏。
2. **非流式调用把超时当总时长上限**：成稿全文 JSON 实测 8k+ token、网关吞吐 ~34-45 tok/s，单次生成 200s+，非流式必撞 `LLM_TIMEOUT=180`；SDK `max_retries=2` 下三连重试 ≈ 9 分钟无输出，叠加 collect 阶段本身静默，即用户看到的「卡死」。`_chat` 改流式聚合（`stream=True` + `include_usage`），超时语义变为相邻 chunk 间隔，慢生成不再被误杀。
3. **LLM_MAX_TOKENS=8000 硬截断**：论文成稿 JSON 超过 8000 token 被拦腰斩断，表现为「JSON 括号不闭合」且修复重试同样截断（预验收实测：paper 两次不合法降级 mock，contest 恰好收在限内 live 成功）。`.env` 设 `LLM_MAX_TOKENS=16000`（网关实测接受 16000/12000），`write()` 检测 `finish_reason=length` 时直接给出可操作报错、跳过无意义修复轮；`.env.example` 注释同步。

配套改动：`app/sources/__init__.py` collect 各源实时打印进度（完成条数/用时/超时/失败——此前首条日志要等 collect 全部结束才打）；`app/pipeline.py` demo 模式 LLM 失败降级 mock 出稿并明确告警（正式 `run_once` 仍报错不降级）。

**验收（`python -m scripts.demo`，全程 ~10 分钟，进度日志逐行可见）：** 论文模块 live 成稿 232.1s——《GMODiff：一步扩散的HDR重建，比LDM快100倍》，抓取 120 条（arXiv 93 条）→ 选用 3 篇 → 配图 3 张；竞赛模块 live 成稿 169.9s——《4场天池赛事速递》，抓取 18 条 → 选用 4 场。六个产物（demo_paper / demo_contest × html / body / md）全部落盘，stderr 零输出，16/16 单测通过。降级路径亦经预验收实测（截断时 mock 兜底出稿、告警文案正确）。遗留：Papers With Code 0 条源告警系该站长期反爬/停更（既有现象，非本次引入）；arXiv 偶发 0 条为公司代理时段性拦截，重跑即恢复。

## 修订（2026-10-20）：控制台三项修复——业界进展失败 / 生成进度可见 / 预览图片 404

用户经 uvicorn 控制台（127.0.0.1:8000）操作后反馈三个问题，逐一修复：

1. **「业界进展」生成失败**：根因是 `db.seen_fingerprints` 把「抓到过」当「用过」——只要条目进过素材库就算 seen，第二次运行时库存全量命中 45 天去重窗口，筛选必然为 0（实测 industry 库存 1363 条全量 seen → 选用 0 条）。修复为只挡 `used_issue IS NOT NULL` 的真·已用条目（实测 seen 1363→3，正常出稿）。配套把筛选失败信息漏斗化：`scoring.funnel_stats` 报告每层各挡多少条（已用去重/分数/关键词/超期）并附最高分候选，`PipelineError` 文案运营可直接对照阈值调参。
2. **生成慢且看不到进度**：进度回调贯通全链路——`run_module(progress=…)` 在 抓取（2–25%，逐源实时报告条数/超时/失败）→ 筛选（28–32%）→ 配图（35–48%）→ 成稿（50–85%，按模型已输出字符数回写）→ 排版（88–97%）五个阶段汇报；`api.py` 把进度与里程碑事件挂进 JOBS，前端每 1.5s 轮询。控制台每个模块卡片内嵌进度条 + 当前阶段 + 已用时，里程碑事件同步写入运行日志；完成态给「打开预览 →」链接（替代常被浏览器拦截的 window.open），失败态红条 + 致命错误摘要（errors 末位）。去掉旧前端 6 分钟假超时（live 成稿实测需 170–230s，假超时会在成功前误报）；`--reload` 热重启丢任务时前端给出可读解释。回调链路全程 try/except 包裹，展示层异常绝不打断任务。
3. **预览页图片全 404**：预览 HTML 里图片是文件系统相对路径（`assets/xx.png`），经 `/preview/{id}` 返回时被浏览器解析成 `/preview/assets/…` 而 404。修复为仅在该接口响应时注入 `<base href="/out/">` 锚定到静态目录；磁盘上的 preview_*.html 保持原样，双击打开仍走同目录相对路径，两种打开方式互不干扰。

**验收（E2E：industry 全流程，mock LLM + demo 不写库，32.4s）：** 进度 2%→97% 单调不回退，5 阶段 11 个里程碑事件逐行可见；抓取 1362 条（BAIR 博客 RSS 1306 + GitHub 开源 56，其余 7 个 RSS 源告警）→ 选用 4 条 → 配图 2 张 → 出稿《底层视觉的工程侧，正在发生什么》；`/preview/{id}` 响应含 base 注入、3 张图片经 `/out/assets/` 全部 200、磁盘文件无 base。RSS 可达性探测（9 源 × 代理/直连）：仅 `bair.berkeley.edu` 经代理可用（HTTP 200）；`openai.com` 被公司代理 MITM 自签证书拦截（SSL verify failed）；`rsshub.app` 及其余源双路皆挂——业界进展现靠 BAIR + GitHub 双源出稿，如需更多 RSS 源需 IT 放行或提供可信 CA。

## 修订（2026-10-21）：实验解读没有可量化数值——素材链路 + 提示词 + 数字核对

用户经控制台生成《Freqformer：用频率分解把去摩尔纹做到 SOTA》后反馈：「关键实验结果解读」「与 SOTA 的对比与代价」两节没有一个可核对的数字，缺乏说服力。逐层排查出五个叠加根因，仅改提示词无效（素材里本就没数据）：

1. **补抓时机错了**：`enrich_figures` 原本在 `collect()` 内、`scoring.select` 之前执行，只补抓 `sorted(score)[:3]`（按全量抓取分数排序的前三），最终入选的熵视条目从未被覆盖——DB 里该期 3 条素材 `extra` 只有 `origin/title_zh/page_url`，`tables` 为 null。
2. **抽表裁列丢方法列**：`extract_tables` 旧 `max_cols=9` 从左裁列，论文 2505.19120 主对比表宽 12 列、表头末列正是 `Freqformer`，方法列被整列砍掉，表虽抽到也无法解读。
3. **提示词允许摆烂**：PAPER_PROMPT 只写「引用素材数字」，没有「必须给表 + 必须给差值」的硬要求，还允许「素材未提供具体数值」这类内部说明。
4. **图片下载拖死整条素材链路**：`HttpClient.download_image` 的 15s 是读间隔超时，慢链路持续吐字节时永不触发（实测单图 70s+），`extract_assets` 卡在图片下载，表格根本没抽。
5. **素材无数字时质量闸跳过**：旧条件 `has_numeric_material(...)` 为假就直接放行，模型自造的对比表没人拦。

**修复：**

- `app/sources/arxiv.py`：`extract_tables` 改为从右补齐保留方法列；新增 `extract_result_snippets`（抽正文里带指标名+数值的结论句，过滤 `nav` 目录导航）与 `_safe_download`（硬超时 12s）；`extract_assets` 先抽表与结论句、再下图片，图片挂了也不赔上表格；`enrich_figures` 移出 `collect()`、放到 pipeline 配图段，只对已入选条目补抓。
- `app/llm/prompts.py`：`FACT_RULES`/`PAPER_PROMPT` 05、04 条重写为硬约束——至少用 table 块原样呈现 1 张素材表、正文合计至少 3 个素材数字且差值必须拿表里两个数逐位现算、禁止自拼表格、禁止「素材未提供/无法量化」话术；新增 `has_numeric_material`/`thin_evidence`/`unsupported_table_numbers`/`unsupported_prose_numbers`/`quant_retry_instruction`/`NO_NUMERIC_RETRY`（素材确无数字时改为禁表格 + 只引相对说法）。
- `app/pipeline.py`：成稿后无条件核对（表格 cell 与 03/04 正文小数），命中就带具体数字清单二次重写；重写后仍有未核实数字则移除该表并记录待人工核对。
- **差值核对三级收紧**：全素材池 → 同一张表同行/同列/同句 → 再按指标名限定作用域（「MUSIQ 55.48，比 AFUNet 高 2.82」只在 MUSIQ 的数值行/列里找配对）。前两级实测过宽：9×12 的表有数千配对，两位小数几乎必被蒙中（2.81 被 25.68−22.87 蒙对，2.82 被另一张表 39.35−36.53 蒙对）。

**验收（E2E：`run_module("paper", demo=True)`，266.2s，live:DeepSeek-V4-Flash）：** 三篇素材均「表 2–3 张、数值结论 8 条」（修复前全部 0 表）；成稿 03 节含 4 列对比表（PU21-PSNR 36.91/35.43/36.68 等）与逐项差值（低 0.23 dB、高 1.25 dB、DISTS 低 0.0017、MANIQA 高 0.0061），04 节点名最强对手 AFUNet（36.91，比 GMODiff 高 0.23 dB）与代价；闸门实测只拦下模型算错的 2.82（55.48−52.70 应为 2.78），0.23/1.25/0.0061/0.30/0.0017/0.92/1.45 等正确差值全部放行。单测 35 项全过。旧稿 `paper-20261021-a1c633` 需重新生成。
